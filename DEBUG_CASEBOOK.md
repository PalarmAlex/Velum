# DEBUG_CASEBOOK.md — Протокол отладки Velum

Журнал разобранных ошибок проекта: симптом → проверенные гипотезы (включая **тупиковые**) → корень → исправление → эвристики.

## Как пользоваться

**Перед поиском причины бага — прочитать раздел «Эвристики» и «Указатель случаев».** Если симптом похож на описанный — начинать с уже известного корня, а не с обхода кодовой базы. Повторение заведомо тупиковой ветки считается ошибкой агента.

**После каждого успешно исправленного бага — добавить случай в этот файл** (шаблон ниже). Это обязательная часть работы, наравне с обновлением справки.

Правила ведения:

- Один случай — 25–45 строк. Кратко, но с якорями в коде (`Файл.cs:строка`) и дословными сообщениями лога.
- **Тупиковые ветки обязательны** и пишутся с причиной опровержения. Ценность протокола — в основном в них.
- Случаи не удалять и не перенумеровывать — номера закрепляются в ссылках.
- Эвристику добавлять в раздел «Эвристики» только если она обобщает случай (иначе — остаётся внутри случая).
- Если новый случай дублирует старый — дополнить существующий, а не заводить новый.

## Эвристики

- **E1. События сохранения SolidWorks приходят и на экспорт.** `FileSaveNotify` / `FileSaveAsNotify2` / `FileSavePostNotify` срабатывают при «Сохранить как → DXF/PDF/STEP» с путём экспорта в `fileName`. Любой обработчик, который **меняет** документ (rebuild, CutList, запись свойств, назначение материала), обязан фильтровать расширение — иначе SolidWorks рвёт собственный PropertyManager. См. случай 1.
- **E2. «Только у X» = ищите ранний выход по типу.** Если баг только у листовой детали (или только у сборок/чертежей), виновник скрыт guard'ом вида `IsSheetMetalPart` / `GetType() == swDoc…`: тяжёлый код выполняется лишь в узкой ветке. См. случай 1.
- **E3. Сообщение лога — это точка *после* работы.** Кодовое слово ошибки (`part_not_saved`) ищется по проекту, затем проверяется, **какие тяжёлые вызовы успели выполниться до него**. Оно может быть «безобидным» итогом, но доказывать выполненную перестройку. См. случай 1.
- **E4. `BeginInvoke` не равен «после завершения команды SolidWorks».** Задача из очереди потока UI выполняется в ближайшем сообщении — когда пользователь уже мог открыть PropertyManager. Отложенное выполнение не спасает от конфликта с активной командой. См. случай 1.
- **E5. `RunOnTaskPaneUiThread` выполняется inline на STA-потоке SolidWorks** (`InvokeRequired == false`), то есть прямо внутри COM-колбэка. Не считать его «безопасным переносом на UI-поток». См. случай 1.
- **E6. Достоверность API проверять рефлексией по interop, а не по памяти.** В `SolidWorks.Interop.sldworks.dll` проекта **нет** `ICommandManager.GetCommandIDs()` (только `GetCommandIDsCount`); `ISldWorks.CommandInProgress` присутствует, но об открытом PropertyManager «Сохранить как» **не** сообщает — для такого guard'а бесполезен. См. случай 1.
- **E7. Сначала логи с временными метками, потом обход кода.** Порядок и наличие/отсутствие записей сужают поиск быстрее чтения обработчиков. Отсутствие записи между двумя событиями — тоже информация: код без логирования по логам не виден.
- **E8. Если `grep_search`/`read_file` и терминал показывают разное — доверять терминалу** (`Test-Path`, `cmd findstr /S`). Индекс файлов может устаревать и показывать несуществующие файлы.
- **E9. Фильтр «нативное ли сохранение» должен быть один на проект.** Раздельные копии предиката в pre-save и post-save расходятся — и пост-путь остаётся без защиты. Общий предикат: `VelumSolidWorksSaveFileNameHelper.IsNativeSavePath`. См. случай 1.
- **E10. Пульсовый такт не должен трогать COM-объекты SolidWorks.** Любой вызов `GetComponents` / перечисление открытых документов / `SyncOpenPathsFromDisk` внутри `OnPulseCompleted` выполняется на UI-потоке SW каждые N секунд и подвешивает интерфейс на 1–2 с при средней сборке. Тяжёлая работа по открытым документам — только на событиях SW (Save / ActiveDocChange) или по команде пользователя. См. случай 2.
- **E11. Переход open→closed нельзя выводить только из `ActiveModelDocChangeNotify`.** Событие — о *смене* активного документа; при закрытии последнего документа нового активного нет, событие не приходит. Состояние, выводимое из событий SW, обязано иметь лёгкую самопроверку на пульсе (один COM-вызов `IActiveDoc2`, без обхода дерева — не нарушает E10). См. случай 3.
- **E12. `GlobalTimer.ClearSystems()` (Dispose контекста ISIDA) обнуляет делегаты событий таймера.** Любой подписчик с флагом «подписан один раз» (`_hooked`) теряет пульс навсегда после перезагрузки ISIDA из настроек (`ReloadIsidaRuntimeWithFreshSettings`). Отписка со сбросом флага — в `VelumSolidEnvironmentBridge.Unhook` (до Dispose контекста); переподписка — через `EnsureAttached` при повторной инициализации. См. случай 3.
- **E13. Пути Windows в C#-литералах — только verbatim `@"...".`.** Одиночный `\` в обычном `"..."` (`"Z:\"`, `"\server"`) ломает строку: компилятор даёт CS1010 («Символ новой строки в константе»), CS1009 («Нераспознанная escape-последовательность»), CS1003 — и сообщения указывают на строку **после** битой кавычки, а не на сам путь. Любой литерал с `\` (буква диска, UNC, `Path.Combine`-образные примеры) писать как `@"Z:\"`, `@"\server\dfs\"`. После правки строк с путями — сразу сборка MSBuild, а не полагаться на «на глаз». См. случай 4.
- **E14. Транспорт тулзов укорачивает `\` в параметрах.** При записи C#-кода через `create_new_file`/`edit_file` последовательность `\` в параметре доходит до файла как `\` (JSON-разыменование), из-за чего `edit_file` может отклонить правку («oldString == newString» / «not found»). Для строк с обратным слэхом: писать verbatim-литералы и/или патчить файл вне тулзов (скрипт с литеральными заменами, кириллица — только в данных, не в шаблоне PowerShell `@"`). См. случай 4.
- **E15. Настройка окружения машины не должна быть списком «все варианты путей».** Список префиксов корня (`Z:\;\ip\dfs\`) не решает переносимость: чтение всё равно использует первый, а запись чужого префикса порождает пути, которые не собираются ни на одной машине. Правильная модель — хранить переносимо (относительно корня), разворачивать локально одной настройкой этой машины. См. случай 5.
- **E16. Ключ-идентификатор записи, зависящий от окружения, делает хранилище непереносимым.** Если `FilePath` записи реестра — абсолютный путь, запись, созданная дома по IP, не открывается на работе (`Z:\`) независимо от локальных настроек. Ключ можно хранить относительным, если <em>все</em> сравнения/поиски идут через нормализатор с достройкой (`NormalizeFilePathKey` → `ToFull`), а прямые потребители (`File.Exists`, `OpenDoc6`, `Process.Start`, HTML-отчёт) достраивают явно. См. случай 5.
- **E17. Нормализатор путей, зависящий от настройки, — горячая точка: кэшировать значение и результат.** Как только сравнение путей стало ходить в настройки (`NormalizeFilePathKey → ToFull → GetRoot → GetSetting`), каждый вызов из цикла по записям реестра превращается в чтение Settings.xml с диска (~0.6 мс), а проход реестра — в тысячи дисковых чтений. Решение трёхуровневое: кэш чтения настройки (TTL + инвалидация при записи), мемоизация корня с версией (`RootVersion` — сигнал сброса внешним кэшам), кэш «значение поля → нормализованный ключ». Побочные ускорители: расширение файла не зависит от корня (не нормализовать путь ради расширения); `File.Exists` на локальном томе — прямой вызов, `Task.Run`/`Wait` с таймаутом — только для UNC; поиск связанной записи по базовому имени — через индекс, а не линейным обходом; «файл изменился» — сигнал только при фактической записи на диск, а не при каждом вызове Save. См. случай 6.

## Случай 1. PropertyManager «Сохранить как → DXF» схлопывается у листовой детали

- **Дата / сборка:** 2026-09-19, `bin\Debug\velum.dll`
- **Симптом:** при «Сохранить как» с расширением DXF панель настроек экспорта мелькает и закрывается, экспорт не выполняется. Нелистовые детали — ОК; с выключенным плагином — ОК; экспорт из формы Velum — ОК.
- **Область:** `SolidHomeostasis\VelumSolidWorksEventsConnector.cs` (`FileSavePostNotify`), `VelumBlankSizeLinksOnSaveCoordinator`, `VelumMaterialAssignOnSaveCoordinator`, `VelumBlankSizePropertyLinksService`.
- **Гипотезы и проверки:**
  1. `VelumBlankSizePropertyLinksService` вызывается из инициализации/проб — **опровергнуто**: `TryEnsure` вызывается только из post-save координатора, рецепта и `TryExport`.
  2. Тяжёлый путь выполняется синхронно внутри `FileSavePostNotify` и мешает сохранению → перенести на `BeginInvoke` (`PostOnTaskPaneUiThread`) — **опровергнуто на практике**: не помогло (причина — E4).
  3. `ModifyNotify`/`RegenPostNotify2` трогают документ при активном PropertyManager → guard по `ISldWorks.CommandInProgress` — **опровергнуто на практике**: API не срабатывает для PropertyManager «Сохранить как», guard был всегда ложью (E6).
  4. Фоновые таймеры / `Application.Idle` / message filter — **опровергнуто**: ловушек нет, `VelumCommandIdleFlusher` работает только при пульсации.
  5. Пост-save обработчики не фильтруют формат сохранения — **корень**.
- **Корень:** «Сохранить как → DXF» порождает `FileSavePostNotify` с `fileName = …\Имя.DXF` → `VelumBlankSizeLinksOnSaveCoordinator` и соседние пост-save вызовы не проверяли расширение → у листовой детали `TryEnsure` делает `ForceRebuild3` + `BodyFolder.UpdateCutList` + запись формул свойств → SolidWorks рвёт собственный PropertyManager страницы DXF.
- **Доказательство:** в логе путь `…Развертка - Деталь1.DXF` **и** сообщение `part_not_saved`. Это кодовое слово генерируется в `VelumBlankSizePropertyLinksService.TryBuildLinkValues` (`:756`), то есть **после** `TryEnsureSheetMetalCutList` (`:87`) — тяжёлый rebuild к этому моменту уже выполнен (E3).
- **Исправление:**
  - `VelumSolidWorksSaveFileNameHelper.IsNativeSavePath(fileName, expectedExtension)` — общий предикат нативного сохранения (E1, E9);
  - фильтр `.sldprt` в `VelumBlankSizeLinksOnSaveCoordinator` и `VelumMaterialAssignOnSaveCoordinator` до тяжёлой работы;
  - `EnsureExternalIdProperty` в `OnModelFileSavePostNotify` гейтится по нативному расширению типа документа (раньше писал свойство на любом не-чертежном сохранении);
  - `IsNativeDrawingSavePath` / `IsNativePartOrAssemblySavePath` сведены к общему предикату;
  - **откачено:** `PostOnTaskPaneUiThread`/`BeginInvoke` (возврат к синхронному `RunOnTaskPaneUiThread`), guard по `CommandInProgress`.
- **Проверка:** новая листовая деталь → «Сохранить как → DXF»: PMP не мигает, DXF создаётся, в логе **нет** строк `Velum blank-size links after save` и `Velum material assign after save`. Обычное «Сохранить → .sldprt»: обе записи есть и с `OK` (авто-починка свойств сохранена).
- **Эвристики:** → E1, E2, E3, E4, E5, E6, E9

## Случай 2. При активной пульсации UI SolidWorks подвисает при работе со сборкой

- **Дата / сборка:** 2026-09-19, `bin\Debug\velum.dll`
- **Симптом:** при активной пульсации (пульс 1 с) каждый тяжёлый пульс стоит 1–2 с блокировки UI на средней сборке (20–50 компонентов). Между тяжёлыми пульсами сборка работает плавно. Воспроизводится только при открытой сборке; без документов — нет.
- **Область:** `Common\ProductRegistry\Integrity\VelumProductRegistryIntegrityScheduler.cs` (`OnPulseCompleted`), `VelumProductRegistryOpenDocumentsScope.TryCollectNormalizedOpenPaths`, `VelumProductRegistryNameSync/ExportMetaSync.SyncOpenPathsFromDisk`.
- **Гипотезы и проверки:**
  1. Тормоза дают сами сканеры проблем реестра (BrokenLink/DXF/PDF) — **опровергнуто**: сканеры уже работают в ThreadPool-тиках (`QueueTick`) с квантами и yield-сигналом; логи тиков вне пульса.
  2. Тормоза в `VelumSolidEnvironmentBridge.OnPulseBeforeGomeostasis` — **опровергнуто**: дерево сборки там не обходится, менять нечего.
  3. Тяжёлая работа в `OnPulseCompleted` шедулера целостности — **корень**: на каждый тяжёлый пульс в open-области такт вызывал `TryCollectNormalizedOpenPaths()` (обход `GetComponents(false)` активной сборки + `GetPathName` каждого компонента через COM), затем `NameSync.SyncOpenPathsFromDisk` + `ExportMetaSync.SyncOpenPathsFromDisk` (загрузка стора + итерация по всем открытым путям), плюс повторный `GetActiveAssemblyComponentCount()` после синхронизации.
  4. Сравнение по `_assemblyComponentCount` (пропуск при неизменном составе) спасает лишь частично — счётчик сбрасывается при Modify/Save, а сам опрос `GetComponents(false)` всё равно выполняется на каждом тяжёлом пульсе: UI-блокировка остаётся.
- **Корень:** тяжёлый пульс → `RunOnTaskPaneUiThread` (на STA-потоке SW, E5) → COM-обход дерева активной сборки (`TryCollectNormalizedOpenPaths`) → синхронизация Name/ExportMeta по всем открытым документам → повторный COM-обход (`GetActiveAssemblyComponentCount`) → UI-поток занят 1–2 с на каждом тяжёлом пульсе.
- **Доказательство:** после удаления из `OnPulseCompleted` COM-блока сборка без изменений поведения тиков: в логах больше нет `Velum registry integrity open-docs sync` в контексте пульса; сохранение `.sldasm` даёт ожидаемый короткий блок только на `TryMirrorSavedAssembly`/`TryMirrorSavedAssemblyStructure`.
- **Исправление:** `OnPulseCompleted` — только счётчики и планирование `QueueTick(null)`; область open/closed берётся из `_openDocumentsScopeActive`, поддерживаемой событиями (`NotifyOpenDocumentsScopeChanged` на `OnActiveModelDocChangeNotify`). Удалены: COM-обход в пульсе, вызовы `SyncOpenPathsFromDisk` из пульса, `_assemblyComponentCount` + сравнение, `GetActiveAssemblyComponentCount`, `_openScopePulseCount`/`OpenScopePulseCount`/`ShouldRunOpenScopeSyncTick`, `NotifyAssemblyStructureChanged` (счётчик больше не читается) и оба её вызова из `VelumSolidWorksEventsConnector` (OnAssyModifyNotify/OnAssyFileSavePostNotify). Синхронизация открытых документов остаётся на: `FileSavePostNotify` (`TrySyncOpenDocumentFromDisk`), `OnActiveModelDocChangeNotify` (`TrySyncActiveDocument`), кнопке «Обновить свойства», пакетном экспорте.

  1. Реально сломан `else`/блок `if` — **опровергнуто**: `read_file` показал корректную структуру; `else` «сломан» лишь потому, что парсер улетел за пределы строки из-за незакрытой кавычки выше.
  2. Битая кодировка/BOM файла — **опровергнуто**: кириллица в комментариях читается нормально, `Logger`/соседи компилируются.
  3. - **Доказательство:** `VelumAppConfig.cs:182` было `… && !trimmed.EndsWith("\")` и `trimmed += "\";` (по одному `\`); `VelumProjectSettingsForm.cs:107` — обычный `"..."` с `Z:\;` и `\dfs\ `. Сообщения CS1010/CS1009 ровно на этих позициях колонок.
- **Исправление:** все три литерала в `GetDocumentRootPathList` и tooltip переведены в verbatim: `@"\"`, `trimmed += @"\";`, `@"… Z:\;\192.168.10.66\dfs\ — "`. Патч выполнен скриптом с литеральными заменами (тулзами править нельзя — см. E14): `EndsWith("\")`→`EndsWith(@"\")`, `trimmed += "\";`→`trimmed += @"\";`, открывающая кавычка tooltip → `@"`.
- **Проверка:** `MSBuild … /t:Build /p:Configuration=Debug` → `EXITCODE=0`, `bin\Debug\velum.dll` собран. Смежное: `GetDocumentRootPathList` по-прежнему дополняет `\` к UNC и `Z:`; tooltip формы настроек читается.
- **Эвристики:** → E13, E14

## Случай 7. Глобальное сканирование не прерывается при открытом (в т.ч. новом несохранённом) документе

- **Дата/сборка:** 2026-09-22, `bin\Debug\velum.dll`.
- **Симптом:** фоновый fleet-скан реестра (BrokenLink/MissingDrawing/DXF/PDF/MissingRegistryEntry) продолжается, хотя в SolidWorks открыт документ: плашки метрик на панели задач остаются «активными». Особенно — новый документ до сохранения, и сразу после первого сохранения нового документа.
- **Область:** `Common\ProductRegistry\Integrity\VelumProductRegistryIntegrityScheduler.cs` (`NotifyOpenDocumentsScopeChanged`, `OnPulseCompleted`, `RunTick`, `TrySyncClosedScopeIfNoOpenDocuments`), `VelumProductRegistryOpenDocumentsScope`, `SolidHomeostasis\VelumSolidWorksEventsConnector.cs` (`OnModelFileSavePostNotify`).
- **Гипотезы и проверки:**
  1. *Событие `ActiveModelDocChangeNotify` не приходит при создании нового документа.* Не корень, но усугубляет: `FileNew`/новая вкладка не гарантируют смену активного.
  2. *Область open выводится из наличия непустых путей.* **Корень:** `NotifyOpenDocumentsScopeChanged` определял `openScope = TryCollectNormalizedOpenPaths().Count > 0`. У нового несохранённого документа `GetPathName()` пуст → множество путей пусто → `openScope=false` → closed-область → сканеры работают при открытом документе.
  3. *После сохранения событие не приходит, closed-область устаревает.* **Корень:** `FileSavePostNotify` не пересинхронизировал область — документ получил путь, а состояние осталось closed.
  4. *Нет симметричного перехода closed→open на пульсе.* **Корень:** был только open→closed (`TrySyncClosedScopeIfNoOpenDocuments`); если событие не дошло (гонка/COM-исключение/открытие через API), область застревала в closed при открытом документе.
- **Корень:** «есть ли открытые документы» выводилось из множества путей и из активного документа, а не из факта наличия любого открытого документа в сессии.
- **Исправление:**
  - `VelumProductRegistryOpenDocumentsScope.HasOpenDocuments()` — `GetFirstDocument()!=null` (1 COM-вызов; true и для несохранённого, и для «невидимого» документа в сессии; нет сессии → false, COM-исключение → true);
  - `NotifyOpenDocumentsScopeChanged` — `openScope = HasOpenDocuments()`, при входе в open форсирует `_tickYieldRequested=1` (текущий квант уступает на следующем элементе);
  - `OnPulseCompleted` — симметричный переход closed→open через `TrySyncOpenScopeIfOpenDocuments()` + `_tickYieldRequested=1`; open→closed переведён с `HasActiveDocument()` на `HasOpenDocuments()`;
  - `RunTick` — живая `HasOpenDocuments()` (маршалл на UI-поток) перед `EnsureStoreLoaded`: закрытие окна между пульсом и стартом тика;
  - `VelumSolidWorksEventsConnector.OnModelFileSavePostNotify` — `NotifyOpenDocumentsScopeChanged()` после синхронизации зеркал (SaveAs даёт документу путь впервые, `ActiveModelDocChangeNotify` не приходит).
- **Замечание (E10):** `HasOpenDocuments()` (`GetFirstDocument`) теперь вызывается на каждом пульсе в closed-области — один COM-вызов, обхода дерева нет, E10 формально соблюдён. При жалобах на подвисание UI в closed-области — искать здесь.
- **Проверка:** сборка MSBuild — успешно. Ручная проверка пользователя: (1) новый документ (Ctrl+N, не сохранять) → скан останавливается в пределах пульса, плашки гаснут; (2) сохранить новый документ → плашки не возвращаются; (3) открыть существующий → плашки гаснут; (4) закрыть последний документ → через N пульсов скан возобновляется.
- **Эвристики:** → E20

## Эвристики

- **E20. «Документ открыт» ≠ «у документа есть путь» и ≠ «есть активный документ».** Факт наличия открытых документов — `GetFirstDocument()!=null` (1 COM-вызов), а не непустой `GetPathName()` и не `IActiveDoc2`: у нового несохранённого документа путь пуст, а «невидимый» (API/batch) документ может быть не активен. Не гейть «сканировать ли реестр» по полям пути/активности — иначе несохранённые и неактивные документы молча выпадают из open-области, и глобальный скан продолжится при открытом документе. Переходы open↔closed должны быть симметричны (событие могло не прийти — дублировать лёгкой проверкой на пульсе) и форсировать уступ фонового кванта (`_tickYieldRequested`). См. случай 7.

### Дополнение к случаю 8 — итерация 3: `IMessageFilter` мёртв, работает `WH_KEYBOARD_LL` (2026-09-23, поздно вечер)

- **Симптом:** после итерации 2 (`IMessageFilter`) Enter по-прежнему не отправляет; в Output SolidWorks **нет ни одной строки `[VelumEnter] filter msg=…`** — `PreFilterMessage` не вызывается ни разу, при установленном в конструкторе фильтре.
- **Диагностика по логам (трассировка `[VelumEnterTB] msg=…` в `WndProc` контрола):**
  - В `WndProc` при нажатии Enter приходят **только** `0x135 wParam=13` (`WM_CTLCOLORBTN`/`WM_CTLCOLOR`) и `0x257 wParam=13` (`WM_KEYUP`) — **`WM_KEYDOWN` (`0x100`) Enter до контрола не доходит вовсе**.
  - `PreFilterMessage` не вызывается ни разу, хотя `Application.AddMessageFilter` успешно отработал в конструкторе (`[VelumEnter] filter installed`).
- **Разбор:**
  1. *`Application.AddMessageFilter` встраивается в петлю SolidWorks и видит `WM_KEYDOWN` до хоста* (посылка E22) — **опровергнуто**: фильтр ставится, но `PreFilterMessage` не вызывается. SolidWorks крутит собственную нативную петлю, которая не дёргает `Application.ThreadContext.RunMessageLoop` → `IMessageFilter` мёртв by design.
  2. *`WndProc` видит `WM_KEYDOWN`* (посылка E21) — **опровергнуто**: Enter гасится хостом **до очереди сообщений контрола** — `WM_KEYDOWN 13` до `WndProc` не доходит, только `WM_KEYUP 13`. Гипотеза «хост гасит Enter как accelerator/default button» **подтверждена логами**.
- **Корень:** оба WinForms-уровня (`WndProc` и `IMessageFilter`) в SolidWorks Task Pane не работают: `PreFilterMessage` не вызывается (нет `Application.RunMessageLoop`), а `WM_KEYDOWN` Enter гасится хостом до очереди сообщений контрола. ## Случай 9. Неатомарная запись конфигов и несинхронизированный `AppendAllText` теряют/перемешивают данные

- **Дата / сборка:** 2026-09-26, `bin\Debug\velum.dll` (задача «анализ кода: баги и слабые места»)
- **Симптом:** (1) `Save()` двух конфигурационных хранилищ писал сразу в целевой файл — при блокировке/падении между сериализацией и записью файл оставался усечённым; (2) статический `VelumSensorPrimariesBuffer` дописывал буферные файлы через `File.AppendAllText` без синхронизации — параллельные вызовы из пульсового цикла ISIDA / таймеров / UI могли перемешать строки или бросить `IOException` (файл занят).
- **Область:** `Common\AssemblyRegistry\VelumAssemblyRegistryColumnStore.cs` (`Save`), `Common\TechRequirements\VelumTechRequirementsStore.cs` (`Save`), `Isida\VelumSensorPrimariesBuffer.cs` (`ReadBufferEntries`, `AppendUniqueToBuffer`, `TryCommit`, `ClearBuffer`, `TryRemoveBufferEntries`, `WriteBufferEntries`).
- **Гипотезы и проверки:**
  1. *Все хранилища уже пишут атомарно* — **опровергнуто**: `VelumAssemblyBomMirrorStore`, `VelumBomChangeLogStore`, `VelumBomExchangeLayout`, `VelumBomStructureStore`, `VelumProductRegistryFolderAutoNames`, `VelumProductRegistryStore`, `RecipeExecutorHandlersBomExport`, `VelumProductRegistryIndexTrace` уже используют temp + `File.Replace`/`File.Move`; но `VelumAssemblyRegistryColumnStore.cs:154` и `VelumTechRequirementsStore.cs:63` писали `File.WriteAllText(FilePath, json)` напрямую (неатомарно).
  2. *`AppendAllText` безопасен без локов* — **опровергнуто**: класс `VelumSensorPrimariesBuffer` статический, lock-объекта не было; `AppendUniqueToBuffer` (137), `TryCommit` (201), `WriteBufferEntries` (327) вызывали `File.AppendAllText`; публичные `ReadBufferEntries`/`ClearBuffer` тоже читали/писали файлы без синхронизации. - **Корень B:** `VelumSensorPrimariesBuffer` — статический класс без единой точки синхронизации; `AppendAllText` из нескольких потоков → гонки, `IOException`, потеря записей при read-modify-write.
- **Доказательство:** `VelumAssemblyRegistryColumnStore.cs:154` (`File.WriteAllText(FilePath, json)`) и `VelumTechRequirementsStore.cs:63` (то же) — единственные неатомарные конфиг-записи; `VelumSensorPrimariesBuffer` — `private static readonly object` отсутствовал, три `File.AppendAllText` без lock.
- **Исправление:**
  - `VelumAssemblyRegistryColumnStore.Save()` и `VelumTechRequirementsStore.Save()` — атомарная запись: `File.WriteAllText(tempPath, json)` + `File.Replace`/`File.Move`, очистка temp в catch, повторный `throw`; добавлен `using System.Text;`. Имя temp — `FilePath + "." + Process.GetCurrentProcess().Id + ".tmp"` (на .NET Framework 4.8 **нет** `Environment.ProcessId` — он появился только в .NET 5; это важно, см. E25).
  - `VelumSensorPrimariesBuffer` — добавлен `private static readonly object AppendSync = new object();`; обёрнуты в `lock (AppendSync)`: `ReadBufferEntries`, `ClearBuffer`, `AppendUniqueToBuffer`, `TryCommit`, `TryRemoveBufferEntries`, `WriteBufferEntries`. Операции read-modify-write (`AppendUniqueToBuffer`, `TryCommit`, `TryRemoveBufferEntries`) держат **весь** блок чтения+расчёта+записи под одним lock, чтобы запись другого потока между чтением и перезаписью не терялась.
- **Проверка:** сборка `Build.cmd Debug` — `EXIT=0`, `velum.dll` собран без ошибок. Смежное: существующие атомарные хранилища не тронуты; логика `TryCommit`/`TryRemoveBufferEntries` (очистка буфера, `ReloadChannelIfReady`) не изменилась, только обёрнута в lock.

## Эвристики (дополнение)

- **E25. На .NET Framework нет `Environment.ProcessId` — использовать `Process.GetCurrentProcess().Id`.** `Environment.ProcessId` доступен только с .NET 5; на .NET Framework 4.8 такой член отсутствует → CS0117/CS0103. В temp-именах и атомарной записи использовать `System.Diagnostics.Process.GetCurrentProcess().Id` (или `Environment.CurrentManagedThreadId` для локальной уникальности в потоке). См. случай 9.

## Эвристики (дополнение)

- **E26. Трёхзначный результат не должен проходить через двоичные обёртки.** `VelumPathExists.Check` различает `Yes/No/Unknown`, но обёртки `FileExists`/`DirectoryExists` (`== Result.Yes`) склеивают `Unknown` с `No`. Любой новый потребитель в сканерах проблем обязан брать трёхзначный `Check` и трактовать `Unknown` как «не доказано — проблему не ставим» (паттерн уже принят для BrokenLink в случае 6.4). Диагностический признак рассинхрона: глобальный сканер ругается, локальная метрика/одиночная проверка той же записи молчит — значит, глобальный путь получает `Unknown`, который кто-то превратил в «нет». См. случай 10.
- **E27. Недожд пакета ≠ таймаут ресурса.** Когда пакет проверок ждётся с общим лимитом (`MaxBatchWaitMs`), незавершившиеся к моменту лимита — это переполнение очереди к семафору, а не «шара не отвечает»: их нельзя ни кэшировать (backoff Unknown закрепляет ложь), ни засчитывать в circuit-breaker ресурса (порог наберётся хвостами больших пакетов при живой шаре). Кэшировать и считать в breaker только реально завершившиеся проверки. Сродни E18: массовая операция не должна превращать собственное переполнение в приговор ресурсу. См. случай 10.

## Случай 11. Счётчик итераций сканирования реестра не сбрасывается на №1 после полного прохода без проблем

- **Дата / сборка:** 2026-09-27, `bin\Debug\velum.dll`
- **Симптом:** при глобальном сканировании реестра без найденных проблем номер итерации (№) в статусе панели продолжает расти и дальше (№5, №6, №7…), хотя полный проход реестра завершён — по замыслу счётчик должен сбрасываться и новый проход начинаться с №1. Воспроизводится всегда, когда полный проход укладывается без прерываний; при открытии документа (abort) сброс работает.
- **Область:** `Common\ProductRegistry\Integrity\VelumProductRegistryIntegrityScheduler.cs` (`RunTick`, `_scanPassInProgress`, `_scanIterationCount`), `VelumProductRegistryBrokenLinkScanner.Tick`, `VelumProductRegistryMissingDrawingScanner.Tick`, `VelumProductRegistryDxfFleetScanner.Tick`, `VelumProductRegistryPdfFleetScanner.Tick` (ветка `quant.Count == 0`).
- **Гипотезы и проверки:**
  1. *Сброс в шедулере не вызывается* — **опровергнуто**: `RunTick` корректно обнуляет `_scanIterationCount` при `!_scanPassInProgress` и сбрасывает флаг по `passCompleted`; ветка `AbortDiscoveryPassesUnlocked` тоже сбрасывает.
  2. *`passCompleted` никогда не становится true* — **корень**: все четыре сканера с курсором при пустом кванте (`quant.Count == 0`) делали `return false` без `CommitPendingPass`, сброса `searchCursor`/`passActive`. Пустой квант возникает в двух ситуациях: (а) от курсора до конца списка не осталось записей, прошедших фильтр сканера (например, в хвосте реестра нет чертежей/деталей — MissingDrawing/DXF/PDF застревают навсегда); (б) курсор уже дошёл до `items.Count` после последнего кванта. В обоих случаях проход фактически завершён, но сканер сообщает «не завершён» → шедулер не сбрасывает `_scanPassInProgress` → счётчик продолжает инкрементироваться.
  3. *Пустой реестр* — **опровергнуто**: ветка `items.Count == 0` уже корректно коммитит и возвращает true — баг только в ветке пустого кванта при непустом реестре.
- **Корень:** два уровня. (A) Во всех четырёх сканерах ветка `if (quant.Count == 0) return false;` не завершала проход при пустом кванте (конец списка по фильтру) — без commit/сброса курсора. (B) Даже после устранения (A) счётчик не сбрасывался: `RunTick` считал `passCompleted &= …` по результатам **всех сканеров одного тика**, но сканеры завершают проход в **разных тиках** (квант 120/80/60/40 и разные фильтры): завершившийся сканер на следующем тике сразу начинал новый проход и возвращал `false` → `passCompleted` никогда не становился `true` → `_scanPassInProgress` не сбрасывался → счётчик инкрементировался вечно.
- **Доказательство:** во всех четырёх сканерах идентичная ветка `if (quant.Count == 0)` → `return false;` до commit-блока; в `RunTick` сброс `_scanPassInProgress` возможен только при `passCompleted == true` всех сканеров в одном тике, что недостижимо при разных размерах квант.
- **Исправление:**
  1. Во всех четырёх `Tick` (BrokenLink, MissingDrawing, DxfFleet, PdfFleet) при `quant.Count == 0` проход завершается: при `passActive` — `CommitPendingPass`/`CommitAllPending` + `passCompleted = true`; затем `searchCursor = 0`, `passActive = false`, `return passCompleted` (зеркально ветке `items.Count == 0`).
  2. В шедулере — флаги `_brokenPassDone`/`_drawingPassDone`/`_dxfPassDone`/`_pdfPassDone`: завершение каждого сканера фиксируется до конца цикла, завершившийся сканер в тиках цикла не запускается; сброс всех флагов и `_scanPassInProgress` — когда все четыре done и дубли обозначений завершились в этом тике; при early-exit по битым ссылкам сетевые проходы помечаются done (иначе цикл не закрылся бы); сброс флагов также в `AbortDiscoveryPassesUnlocked`.
- **Проверка:** сборка MSBuild Debug — EXIT=0. Ручная: полное сканирование реестра без проблем — после завершения прохода статус показывает «Сканирование №1» (новый цикл), а не продолжение нумерации; при открытии документа во время прохода abort по-прежнему сбрасывает всё; при наличии битых ссылок цикл тоже закрывается (early-exit помечает сетевые проходы done).
- **Итог ускорения (продолжение случая):** после фикса счётчика профиль скорости: реестр ~4850 записей, квант 400/слоты 64 — полный цикл за 13 тиков (~75 с). Затем квант поднят до 1000, дефолт `ScannerProbeConcurrency` 64 (было 16). Квант и параллелизм вынесены на форму настроек проекта (вкладка «Адаптер»: «Параллелизм проверок сканера» = `ScannerProbeConcurrency`, «Квант сканирования (строк)» = `ScannerBatchSize`) — тюнинг без пересборки; сканеры читают `VelumAppConfig.ScannerBatchSize` вместо констант. Устаревший дефолт 16 в `EnsureScannerProbeConcurrencySetting` заменён на 64, добавлен Ensure для `ScannerBatchSize=1000`; но если в Settings.xml уже записан `ScannerProbeConcurrency=16`, значение файла перекрывает дефолт — менять на форме или руками в XML.
- **Эвристики:** → E28, E29, E30

## Случай 13. Прогресс «пройдено X из Y»: прыгающие числа и залипание на Y до конца цикла

- **Дата / сборка:** 2026-09-27, `bin\Debug\velum.dll`
- **Симптом:** статус панели показывал непрогрессивные числа: 1000 → 2450 → 4340 → 4850 → 4850 и сброс, хотя курсоры по логам шли ровно 1000/2000/3000/4000. На последних двух тиках залипало на 4850 (весь реестр), пока шёл ещё один сканер.
- **Область:** `VelumProductRegistryIntegrityScheduler.ScanProgressCursor` (агрегация курсоров в число прогресса).
- **Корень:** метрика брала **max** по курсорам сканеров (+ done = total). Два дефекта: (1) max показывает лидера, а не отставшего — у сетевых сканеров (drawing/dxf/pdf) курсор это индекс в общем списке, а квант — отфильтрованные записи (чертежи/детали), поэтому их курсор за квант перескакивает через тысячи строк (dxf=4053 уже после 1-го тика); панель читается по пульсам и ловит разные фазы одного тика → «прыжки» 2450/4340. (2) Вклад done=total при max означает: как только часть сканеров done, прогресс = total и залипает, пока идёт последний (BrokenLink).
- **Исправление:** метрика — **min по незавершившимся** (not-done) сканерам, done-сканер даёт вклад total; если все done — total. min по not-done = самый медленный = честный прогресс цикла, монотонный (курсоры not-done только растут, done-вклад = total ≥ любой курсор). Косметика: на старте цикла курсоры ещё 0, а первый квант уже в работе — при min == 0 показывается размер кванта (`ScannerBatchSize`), иначе весь первый тик статус выглядит как «0 пройдено».
- **Проверка:** сборка MSBuild Debug — EXIT=0. Прогресс на тех же логах: 1000 → 2000 → 3000 → 4000 → 4850 → сброс (по отставшему BrokenLink).
- **Эвристики:** → E32

## Эвристики (дополнение)

- **E28. «Пустой квант» курсорного прохода — это конец прохода, а не «нет работы».** В курсорных сканерах (курсор + pending-проход) пустой квант означает, что от курсора до конца списка не осталось записей по фильтру — полный проход завершён и обязан коммитить pending, сбрасывать курсор/флаг прохода и возвращать «проход завершён». `return false` при пустом кванте навсегда замирает проход (и любые агрегаты шедулера вроде «счётчик итераций» не сбрасываются). Диагностический признак: ветка `items.Count == 0` коммитит, а ветка `quant.Count == 0` — нет; симптом проявляется только при беспроблемном полном проходе. См. случай 11.
- **E29. «Все сканеры завершились в одном тике» — недостижимое условие при разных квантах.** Агрегат вида `passCompleted &= Scanner.Tick(...)` по нескольким курсорным сканерам требует завершения всех проходов в одном и том же тике — но кванты/фильтры у сканеров разные, и завершившийся сканер на следующем тике начинает новый проход и снова возвращает false. Завершение каждого сканера нужно фиксировать флагами «done» до конца цикла (сканер не перезапускается, пока цикл не закрыт), а не сводить в один тик. Диагностический признак: счётчик итераций растёт вечно при живом сканировании; сброс никогда не наступает, хотя каждый сканер по отдельности проходит реестр от начала до конца. См. случай 11.
- **E30. Настройки производительности, заточенные под конкретную машину, выносить в Settings.xml и на форму.** Квант прохода и параллелизм проверок, подобранные экспериментально (квант 1000, слоты 64, 13→~5 тиков на ~4850 записей), нельзя оставлять константами в коде: у другой машины/сети/диска оптимум другой. Правильное место — ключи `ScannerBatchSize`/`ScannerProbeConcurrency` в Settings.xml (Ensure-методы для старых конфигов) + поля на вкладке «Адаптер» формы настроек с валидацией и ToolTip. Диагностический признак: «ускорение» требует пересборки и правки констант в каждом сканере. См. случай 11.
- **E31. Вердикт агрегата — по флагу цикла, а не по флагам участников.** Если участники (сканеры) завершаются в разных тиках, их индивидуальные флаги «проход активен» сбрасываются поодиночке — дизъюнкция таких флагов «провисает» в false между тиками, и UI-вердикт («проблем нет»), повешенный на неё, показывается преждевременно. Вердикт по агрегату нужно вешать на флаг всего цикла, который держится до закрытия всех участников. Диагностический признак: итоговый вердикт «мигает» в середине цикла, пока счётчик итераций ещё растёт. См. случай 12.
- **E32. Прогресс нескольких курсорных проходов — min по незавершённым, а не max.** Когда несколько сканеров с независимыми курсорами идут параллельно и завершаются в разное время, число «прогресса» для UI — это min по курсорам ещё не завершившихся (завершившийся = весь объём). max показывает лидера и «прыгает» (у фильтрующих сканеров курсор — индекс в общем списке, перескакивает через пропущенные записи), а вклад «завершён = весь объём» при max даёт залипание на финальном значении, пока идёт отставший. Диагностический признак: прогресс немонотонен или залипает на Y при незавершённом сканере. См. случай 13.
- **E33. «Выключено по умолчанию» ≠ «удалено из набора».** Если настройка-список нормализуется по эталонному перечню ключей (`Normalize` докидывает отсутствующие), снятие поля с поддержки требует убрать ключ из эталона **и** добавить вычистку осиротевших колонок (`RemoveAll` по «нет в эталоне»). Иначе нормализация вечно возвращает снятое поле, а миграция формата лишь выключает его (колонка остаётся в UI включаемой). Диагностический признак: «убранное» поле по-прежнему видно в окне настроек. См. случай 14.

## Случай 17. Диалог «Обзор» (выбор каталога) виснет при битой сетевой ссылке; сетевые диски не показываются вовсе

- **Дата / сборка:** 2026-09-27, `bin\Debug\velum.dll` (после случая 16)
- **Симптом:** после случая 16 пользователь при битой ссылке нажимает «Обзор» — форма выбора каталога (`VelumFolderBrowser.SelectOnlyFolderForm`) надолго зависает. ## Эвристики (дополнение)

- **E36. Гардами существования покрыты не все потребители — проверять весь вызываемый граф, включая диалоги.** `VelumPathExists` защищает только тот код, который его использует; формы-диалоги (браузеры каталогов, селекторы) с прямыми `Directory.Exists`/`EnumerateDirectories`/`DriveInfo.IsReady` в UI-потоке остаются точками зависания даже после перевода остальной цепочки на гарды. Диагностический признак: зависает конкретный диалог, а не форма — искать прямой IO внутри его конструктора и обработчиков (`PopulateRoots`, `BeforeExpand`, валидация ввода). Сетевые диски в списках дисков показывать всегда с пометкой доступности: `IsReady` и `VolumeLabel` на отключённой шаре сами блокируют поток, фильтр «не готовые — скрыть» одновременно и зависает, и прячет нужный диск. См. случаи 10, 15, 17.

- **E34. Гард существования пути не покрывает чтение/запись/создание каталога.** `VelumPathExists.Check` защищает только проверку существования; `File.ReadAllText`/`File.WriteAllText`/`Directory.CreateDirectory` на недоступной шаре блокируют поток так же (десятки секунд), и обязаны иметь собственные таймаут-обёртки (`ReadAllTextWithTimeout`/`WriteAllTextWithTimeout`/`TryCreateDirectory`). Диагностический признак: зависание при живом `VelumPathExists` — значит, в цепочке остался прямой IO. См. случай 15.
- **E35. Признак недоступного пути в форме — правка свойств существующих контролов, а не новые контролы.** Индикатор доступности пути в плотно сверстанной вкладке делается подсветкой текста поля (`ForeColor = Color.Red`) и дописыванием примечания в существующий ToolTip (`GetToolTip` + проверка на дубль), без добавления label'ов и правок Designer — компоновка не меняется. Обновление UI из фоновой проверки — только через `BeginInvoke` с проверкой `IsDisposed`. Индикатор обязан быть **снимаемым**: ветка «доступен» в применении статуса не менее важна, чем «недоступен» — статус, выставленный фоновой проверкой, сбрасывается при изменении значения поля (например, выбором каталога через «Обзор»). См. случаи 15, 16.

## Случай 18. «DXF устарел» показывается у всех деталей сборки после правки одной

- **Дата / сборка:** 2026-09-28, `bin\Debug\velum.dll`
- **Симптом:** открыли сборку, отредактировали одну деталь с выгрузкой DXF, сохранили и закрыли сборку, включили глобальное сканирование — плашка «DXF устарел» появляется у ВСЕХ деталей сборки, хотя изменена одна. На локальной метрике каждой неправленой детали (при открытии в SW) — тихо.
- **Область:** `ReactiveCore\VelumExportDocumentationGeometryStampHelper.cs` (`NotifyPartGeometryModified`, `TryIsDxfOutdated`), `ReactiveCore\Export\VelumDxfArtifactResolver.cs`, `Common\ProductRegistry\Integrity\VelumProductRegistryDxfFleetScanner.cs`, `Common\ProductRegistry\VelumProductRegistryExportMetaSync.cs`.
- **Гипотезы и проверки:**
  1. *Сохранение сборки пишет pending-штамп в реестр всем деталям* — **опровергнуто**: `TrySyncStampsAfterSave`/`TrySyncOpenDocumentFromDisk` пишут строго ОДНУ запись по `GetPathName()` сохраняемого файла; для сборки `ApplyDxfMeta = false`; события Save сборки (`VelumSolidWorksEventsConnector`) к детям не расходятся.
  2. *Ложный pending-штамп в CPM деталей* — **корень**: `TryIsDxfOutdated` = `pending > export`. Pending писался при работе со сборкой через `RegenPostNotify2`/`ModifyNotify` → `NotifyPartGeometryModified`. После закрытия последнего документа `SyncDocumentsScope` легально чистит кэш проблем (случай 7 / E20), а флот-сканер `VelumProductRegistryDxfFleetScanner.IsDxfOutdated` пересобирает список по зеркалу `items.json` — уже с ложными pending, которые кэш больше не прикрывает.
  3. *Корень A — pending уходит в служебную развёртку* — **подтверждено**: `NotifyPartGeometryModified` резолвил цель через `TryGetActiveConfigurationName` (сырое имя активной) → при развёртке pending писался в конфигурацию `SM-FLAT-PATTERN`, которую флот-сканер не читает; в родительскую (читаемую) — нет, но штамп всё равно ложный.
  4. *Корень B — смена активной конфигурации* — **подтверждено**: переключение активной (Конфиг1→Конфиг2) поднимает `GetUpdateStamp` и порождает Regen/Modify → ложный pending в новую активную конфигурацию мульти-конфиг деталей (сам файл не менялся).
- **Корень:** два пути ложного pending в `NotifyPartGeometryModified`: (A) цель резолвилась сырым именем активной конфигурации (развёртка `SM-FLAT-PATTERN` вместо читаемой родителем); (B) сама смена активной конфигурации поднимала штамп обновления и давала Regen/Modify, который трактовался как изменение геометрии.
- **Доказательство:** `TryIsDxfOutdated` сравнивает pending и export по resolved-конфигурации; до правки `NotifyPartGeometryModified` брал `TryGetActiveConfigurationName(modelDoc)` напрямую. После закрытия последнего документа кэш проблем пуст (E20), и флот-сканер читает pending из зеркала напрямую — ложные штампы видны все разом.
- **Исправление:**
  - `NotifyPartGeometryModified`: цель — `VelumDxfArtifactResolver.TryResolveDefaultExportConfigurationName(modelDoc)` (развёртка→родитель, пусто→первая пользовательская) вместо сырого `TryGetActiveConfigurationName`;
  - baseline активной конфигурации `_activeConfigNameByDoc` + синхронизация в `CaptureFlatPatternFoldSignature`;
  - новый `TryAbsorbActiveConfigurationChange(modelDoc)`: сравнивает активную с baseline, обновляет baseline; при фактической смене возвращает true → `NotifyPartGeometryModified` только переснимает fold-подпись и выходит (pending НЕ пишется); первый контакт — только фиксирует baseline (false);
  - перед `CaptureFlatPatternFoldSignature` в `NotifyPartGeometryModified`: `if (TryAbsorbActiveConfigurationChange(modelDoc)) { CaptureFlatPatternFoldSignature(modelDoc); return; }`.
- **Проверка:** `Build-Velum.ps1 Debug` → EXIT=0, `velum.dll` собран. Ручная на машине с SW: сборка с мульти-конфиг деталями → отредактировать одну деталь + DXF → сохранить/закрыть сборку → глобальный скан → «DXF устарел» только у изменённой; переключение активной конфигурации без правки файла pending не поднимает; в `%ProgramData%\VELUM\` нет `DxfGeometryUpdateStamp updated due to pending > export` по неправленым деталям.
- **Эвристики:** → E37, E38

## Эвристики (дополнение)

- **E37. Служебные конфигурации (развёртка `SM-FLAT-PATTERN`) не читают флот-сканеры — цель штампа резолвить к экспортируемой конфигурации, а не к активной.** `TryGetActiveConfigurationName` возвращает сырое имя активной; если она активна развёртка листовой детали, pending/штамп уйдёт в конфигурацию, которую `DxfFleetScanner` не перечитывает, — и вердикт «устарел» рассинхронизируется. Для записи DXF-штампа нужен `TryResolveDefaultExportConfigurationName` (развёртка→родитель, пусто→первая пользовательская). Диагностический признак: ложный «DXF устарел» у деталей, где менялась только развёртка/плоскость. См. случай 18.
- **E38. Смена активной конфигурации поднимает `GetUpdateStamp` и даёт Regen/Modify — это НЕ изменение геометрии, pending писать нельзя.** Переключение активной конфигурации мульти-конфиг детали SolidWorks трактует внутренне как обновление (растёт update-штамп, приходят Regen/Modify-колбэки). Если `NotifyPartGeometryModified` на них пишет pending — любая правка/открытие сборки с переключением конфигов порождает волну ложных «DXF устарел» по всем деталям. Нужен baseline активной конфигурации на документ и подавление pending на фактической смене активной (первый контакт — только зафиксировать baseline). См. случай 18.
