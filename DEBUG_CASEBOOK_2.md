# DEBUG_CASEBOOK.md — Протокол отладки Velum

Журнал разобранных ошибок проекта: симптом → проверенные гипотезы (включая **тупиковые**) → корень → исправление → эвристики.

## Как пользоваться

**Перед поиском причины бага — прочитать раздел «Эвристики» и «Указатель случаев».** Если симптом похож на описанный — начинать с уже известного корня, а не с обхода кодовой базы. Повторение заведомо тупиковой ветки считается ошибкой агента.
**После каждого успешно исправленного бага — добавить случай в этот файл** (шаблон ниже). Это обязательная часть работы, наравне с обновлением справки.

Правила ведения:

- Один случай — 25–45 строк. Кратко, но с якорями в коде (`Файл.cs:строка`) и дословными сообщениями лога.
- **Тупиковые ветки обязательны** и пишутся с причиной опровержения. Ценность протокола — в основном в них.
- Случаи не удалять и не перенумеровывать — номера закрепляются в ссылках.
- Эвристику добавлять в раздел «Эвристики» только если она обобщает случай (иначе — остаётся внутри случая).
- Если новый случай дублирует старый — дополнить существующий, а не заводить новый.

## Шаблон случая

```
## Случай N. <Краткий симптом — как его формулирует пользователь>

- **Дата / сборка:**
- **Симптом:** что видно пользователю; при каких условиях воспроизводится и при каких нет.
- **Область:** подсистема, классы, события.
- **Гипотезы и проверки:** нумерованный список; для каждой — что проверено, чем (код/лог/рефлексия), итог «корень» / «опровергнуто: причина».
- **Корень:** причинно-следственная цепочка, одно звено на строку.
- **Доказательство:** лог/строка кода, которая однозначно подтверждает корень.
- **Исправление:** файлы, суть правки, что откачено из неудачных итераций.
- **Проверка:** как убедиться, что починено и что не сломано смежное.
- **Эвристики:** → N, N (номера добавленных правил).
```

## Случай 19. Обмен с 1С: сломанный вызов в TryMirrorSavedPart, рассинхрон регистра ExternalId, вечные pending и дубли в журнале изменений

- **Дата / сборка:** 2026-09-28, `bin\Debug\velum.dll` (аудит обмена BOM с 1С по запросу «есть ли скрытые баги»)
- **Симптом:** (1) проект не компилировался — в `TryMirrorSavedPart` вместо `store.Upsert(...)` стоял несуществующий вызов `mirrorStore.SetValue` (незакоммиченный регресс незавершённой правки); (2) смена регистра ExternalId (например, `abc123` → `ABC123`) порождала ложный update-поток в `1C_bom_*.csv` без реального изменения; (3) pending-записи журнала с пустым `ParentExternalId` (ExternalId родителя очистили после накопления очереди) зависали в `bomChangeLog.json` навсегда; (4) повторное сохранение сборки без изменений плодило дубли невыгруженных операций add/update/delete.
- **Область:** `Common\AssemblyRegistry\VelumAssemblyBomMirrorCoordinator.cs` (`TryMirrorSavedPart`), `VelumAssemblyBomStructureCoordinator.cs` (`AppendChanges`), `VelumBomChangeLogStore.cs`, `VelumBomExchangeHierarchyRanker.cs` (`_rankByParentExternalId`), `VelumBomExchangeStructureProjector.cs` (`StructuresByParentExternalId`, `DeferredParentExternalIds`).
- **Гипотезы и проверки:**
  1. *`mirrorStore.SetValue` — осмысленный API соседнего класса* — **опровергнуто**: grep по AssemblyRegistry — единственный вызов `mirrorStore` в этом файле, локальная переменная называется `store`; в `TryMirrorSavedAssembly` используется `store.Upsert` (строка ~85). Регресс обрывка правки.
  2. *Смена регистра ExternalId — экзотика, можно не чинить* — **опровергнуто кодом**: зеркало/структура сравнивают Identity `OrdinalIgnoreCase`, а `AppendChanges` сравнивал `ChildExternalId` по `Ordinal`, `_rankByParentExternalId` и `StructuresByParentExternalId` — `Ordinal`-словари. Один и тот же ExternalId в разных регистрах = «изменился» в журнале, но «не изменился» в хэше → ложный update-поток в 1С без смены хэша. Единый регистронезависимый стиль остального кода нарушен в трёх местах.
  3. *Pending без ParentExternalId всё же выгрузится когда-нибудь* — **опровергнуто трассировкой**: `VelumBomExchangeStructureProjector.Select` пропускает записи с пустым `ParentExternalId` (`GetEntriesWithDiscrepancy` их тоже исключает), а `PurgeExportedOlderThan` чистит только `Exported=true`. Запись `!Exported` с пустым родителем невыгружаема по определению → вечная очередь.
  4. *Дубли в журнале безвредны, 1С сама схлопнет* — **опровергнуто**: форма экспорта и CSV показывают дубли до первой выгрузки; идентичная операция с новым Guid не несёт информации, только шум.
- **Корень:**
  - обрывок незавершённой правки в `TryMirrorSavedPart` (синтаксис сломан);
  - три разрозненных `Ordinal`-сравнения ExternalId против `OrdinalIgnoreCase` во всём остальном обмене;
  - отсутствие ветки «невыгружаемое pending» в очистке журнала (`!Exported` считался вечным по определению, без проверки выгружаемости);
  - `AppendChanges` писал новую запись с новым Guid на каждое зеркалирование, без проверки уже стоящей в очереди идентичной операции.
- **Доказательство:** `VelumAssemblyBomMirrorCoordinator.cs:185` — `mirrorStore.SetValue` без скобок/присвоения (CS1002/CS0117); `VelumAssemblyBomStructureCoordinator.cs` — `string.Equals(..., StringComparison.Ordinal)` на `ChildExternalId`; `VelumBomChangeLogStore.Save` до правки вызывал только `PurgeExportedOlderThan`.
- **Исправление:**
  - `TryMirrorSavedPart`: восстановлен `store.Upsert(...)` с теми же аргументами;
  - `AppendChanges`, `_rankByParentExternalId`, `StructuresByParentExternalId`, `DeferredParentExternalIds` — `OrdinalIgnoreCase` (единый стиль обмена);
  - `VelumBomChangeLogStore.PurgeUnexportablePending()` — удаление `!Exported`-записей с пустым `ParentExternalId` (вызывается из `Save()` после `PurgeExportedOlderThan`); при ручном возврате ExternalId родителя следующее зеркалирование структуры создаст корректную запись заново;
  - `VelumBomChangeLogStore.HasPending(action, parentExternalId, childIdentity)` — проверка идентичной невыгруженной операции; `AppendChanges` вызывает её перед Append для add/update и delete — повторное сохранение без изменений очередь не раздувает.
- **Проверка:** `Build-Velum.ps1 Debug` → EXIT=0. Ручная: (1) сохранить отдельно открытую деталь → в `bomMirror.json` появляется карточка, в логе `Velum bomMirror part OK`; (2) сменить регистр ExternalId ребёнка → записи журнала не плодятся, хэш структуры меняется один раз; (3) очистить ExternalId родителя с накопленной очередью → при следующем зеркалировании/`Save()` pending-записи без родителя исчезают из `bomChangeLog.json`; (4) повторно сохранить сборку без изменений → число pending-записей не растёт.
- **Эвристики:** → E39, E40

## Эвристики (случай 19)

- **E39. «Невыгруженное — вечное» ложно: у очереди обязана быть ветка «невыгружаемое».** Любое хранилище-очередь с инвариантом «!Exported не удаляется никогда» накапливает записи, которые не могут быть выгружены в принципе (пустой ключ связки с 1С). Очистка обязана различать «ожидающее выгрузки» и «невыгружаемое» (пустой ParentExternalId) и удалять второе — иначе очередь растёт вечно. Диагностический признак: pending-записи старше недель в журнале при живом обмене. См. случай 19.
- **E40. Регистронезависимость ключа должна быть одинаковой во всех точках сравнения конвейера.** Если Identity/пути сравниваются `OrdinalIgnoreCase`, а ExternalId где-то по `Ordinal` (сравнение строк, словари ранжирования/отбора), смена регистра одного и того же ключа даёт ложное «изменение» в одном звене и «неизменность» в другом — рассинхрон журнала и хэшей без реальных данных. Правило: один ключ конвейера — один comparer на весь конвейер. Диагностический признак: update-поток в обмен при неизменном хэше. См. случай 19.
- **E41. «Не удалось прочитать» ≠ «пусто»: хранилище обязано различать отсутствие файла и сбой чтения.** Любой гейт с таймаутом (`ReadAllTextWithTimeout` и аналоги) возвращает один и тот же результат и для «файла нет», и для «сеть не ответила». Хранилище, которое трактует оба как «пустые данные», на сетевых томах подменяет живые данные пустыми и (хуже) сохраняет их обратно. Правило: чтение с таймаутом возвращать трёхзначным результатом (`Success/FileMissing/Failed`); на `Failed` — прерывать загрузку исключением, не трогая ни память, ни диск. Диагностический признак: данные «то есть, то нет» на сетевом томе; дефолтный файл-пустышка на диске после сбоя. См. случай 20.
- **E42. Автовосстановление дефолта в Load() допустимо только при доказанном отсутствии данных.** Ветка «если набор пуст — создать дефолт и сохранить» в `Load()` безопасна лишь для `FileMissing` (первый запуск). Для `Failed`/битого JSON она превращается в уничтожитель данных: Save() перезаписывает живые файлы дефолтом. Плюс гард уровня записи: Save() обязан отказываться писать файл, если записываемый набор заведомо не может быть легитимным (0 каталогов реестра при невозможности удалить последний через UI). Диагностический признак: файл с «сигнатурой дефолта» (NextId=2, единственный корень) при том, что в UI данные есть. См. случай 20.

## Случай 20. Реестр документов: дерево загружено, список пуст («Записей: 0»); folders.json затёрт одним корнем после VPN-сбоя

- **Дата / сборка:** 2026-09-28, `bin\Debug\velum.dll` (жалоба: «список пуст, дерево загрузилось; путь в настройках не красный, значит доступен»)
- **Симптом:** (1) при открытии формы реестра список записей пуст при полном дереве каталогов; нестабильно — при следующих открытиях список появлялся; (2) в какой-то момент `folders.json` на диске оказался с `NextId:2` и единственным корнем «Изделия» (все каталоги стёрты), при этом в UI дерево и записи ещё показывались (из памяти); (3) при подключении отладчиком — вылет `System.IO.IOException` «не удалось создать tmp-файл items.json, каталог недоступен»; (4) «Проверка путей» не подсвечивала пути красным.
- **Область:** `Common\ProductRegistry\VelumProductRegistryStore.cs` (`Load`, `Save`), `ReactiveCore\Export\VelumPathExists.cs` (`ReadAllTextWithTimeout`), `VelumProductRegistryForm.cs` (`TryPrepare`), `VelumProductRegistryProblemsForm.cs` (`OnOpenRegistryClick`).
- **Гипотезы и проверки:**
  1. *Виноваты настройки сканера (64 параллелизма / квант 1000–2000 строк)* — **опровергнуто**: `ScannerProbeConcurrency` и квант влияют только на сканеры целостности и индексацию, а не на `Load()` стора; связь «2000 → нестабильно» — косвенная нагрузка на сеть/шару.
  2. *Фильтр списка или отсутствие записей у выбранного узла* — **опровергнуто**: фильтр стоял «(все)», статусы при открытии очищаются (`_pathStatuses.Clear()`); на скрине «Записей: 0» при полном дереве.
  3. *«Применить bootstrap»/«Индексирование» не нажаты* — **тупиковая и недостоверная**: таких кнопок/механизма на форме нет; это была ошибка агента (выдуманный код). Не повторять.
  4. *Таймаут чтения items.json (1.5 с) → null → «пустой реестр»* — **подтверждено как корень**: `ReadAllTextWithTimeout` по таймауту возвращает `null`, `Load()` трактовал это как отсутствие данных, создавал дефолтный корень с `_foldersDirty=true` и сохранял — затирая живой `folders.json`. Для items аналогично: любое изменение записи после «пустого» Load сохранило бы пустой `items.json`. Нестабильность списка — та же причина: таймаут 1500 мс на VPN-шаре то проходит, то нет.
- **Корень:**
  - `ReadAllTextWithTimeout` возвращает `null` и на «файла нет», и на «чтение не успело/ошибка» — причины неразличимы;
  - `Load()` в старом коде сначала очищал память, затем читал оба файла с `?? new ...File()` — сбой чтения выглядел как легитимный пустой реестр;
  - ветка `if (_folders.Count == 0)` в `Load()` создавала корень «Изделия» с `_foldersDirty=true` и вызывала `Save()` — на «пустом» состоянии это перезаписывало живой файл одним корнем;
  - таймаут 1500 мс на большом `items.json` через VPN — реальный, но не первопричина: даже при срабатывании нельзя было молча подменять данные пустыми.
- **Доказательство:** восстановленный из бэкапа до затирания `folders.json` имел полный набор каталогов; текущий — ровно сигнатура дефолтной ветки `Load()` (`NextId:2`, корень «Изделия»); `VelumPathExists.ReadAllTextWithTimeout` возвращает `null` при `!task.Wait(timeoutMs)`; `Load()` до правки: `ReadJson(...) ?? new VelumProductFolderFile()` + `_foldersDirty = true; Save()` при пустом наборе.
- **Исправление:**
  - `VelumPathExists`: добавлены `ReadTextOutcome` (`Success`/`FileMissing`/`Failed`) и `ReadAllTextWithStatus` — «файла нет» и «чтение не удалось» различимы; FileNotFound/DirectoryNotFound внутри задачи — отсутствие, прочие исключения — сбой;
  - `Store.Load()`: оба файла читаются **до** очистки памяти; при `Failed` (любой из двух) — `IOException`, память и диск не тронуты; чтение успешное, но пустое (`FileMissing`) — легитимный пустой реестр (первый запуск); битый JSON — тоже `IOException` через `ParseJson` (частично читаемый файл не должен выглядеть пустым);
  - `Store.Save()`: гард — запись `folders.json` с нулём каталогов запрещена (`InvalidOperationException`); через UI последний каталог удалить нельзя (`DeleteFolderCascade` оставляет корень), так что пустая запись сюда легально не доходит;
  - `TryPrepare` (форма): `IOException` от `Load()` перехвачен — окно с текстом, открытие прервано (`return false`), trace-метка `form.prepare.load.failed`;
  - `ProblemsForm.OnOpenRegistryClick`: перечитывание `_store.Load()` обёрнуто в try/catch с сообщением; фоновые потребители (`NameSync`, `ExportMetaSync`, `IntegrityScheduler.EnsureStoreLoaded`, `BomExchangeRegistryIndex`, `PdfBatchDiagnosticsForm`) уже имели catch — исключение просто отменяет проход.
- **Проверка:** `Build-Velum.ps1 Debug` → 0 ошибок. Ручная: (1) при живой шаре форма открывается, список и дерево на месте; (2) имитация сбоя (отключить VPN перед открытием) — вместо пустой формы: сообщение «Не удалось загрузить реестр документов», файлы `folders.json`/`items.json` на диске **не изменяются** (проверить timestamp); (3) после восстановления сети форма открывается без потери данных; (4) фоновые зеркалы при сбое пишут Warning в лог и не трогают файлы.
- **Эвристики:** → E41, E42

## Случай 21. Панель агента: «Сканирование №1, №2, №3 …» до бесконечности при пустом реестре (папки/файлы доступны, записей 0)

- **Дата / сборка:** 2026-09-29, `bin\u005cDebug\u005cvelum.dll` (жалоба: «реестр по путям доступен, но items.json/folders.json пустые — сканирование идёт, счётчик крутится, хотя реально сканировать нечего»)
- **Симптом:** на панели задач статусная строка `Сканирование №N (P пул.): …` с растущим `N = 1, 2, 3 …` до бесконечности, когда реестр успешно прочитан, но не содержит ни одной записи. Реальной работы сканеров нет (записей-то ноль).
- **Область:** `Common\u005cProductRegistry\u005cIntegrity\u005cVelumProductRegistryIntegrityScheduler.cs` (`RunTick`, `EnsureStoreLoaded`), сканеры `VelumProductRegistryBrokenLinkScanner`/`MissingDrawingScanner`/`DxfFleetScanner`/`PdfFleetScanner` (`Tick` при `items.Count==0`), `Common\u005cVelumAgentTaskPane.cs` (`UpdateRegistryScanStatus`).
- **Гипотезы и проверки:**
  1. *Счётчик инкрементируется на пульсе UI* — **опровергнуто**: `Interlocked.Increment(ref _scanIterationCount)` стоит только в `RunTick` (фоновый тик), на пульсе лишь `QueueTick`.
  2. *Сканеры при пустом реестре завершают проход (`return true`), и цикл просто быстро повторяется* — **опровергнуто кодом**: у курсорных сканеров ветка `if (items.Count == 0)` возвращает `passCompleted=true` **только если `passActive` уже true** (коммит pending). При пустом реестре в первом тике `passActive==false`, значит возвращается `false`; флаги `_brokenPassDone`/`_drawingPassDone`/`_dxfPassDone`/`_pdfPassDone` никогда не выставляются → условие закрытия цикла `_brokenPassDone && … && passCompleted` в хвосте `RunTick` ложно, `_scanPassInProgress` остаётся `true`, и на каждом следующем тике счётчик растёт. (Дубль-сканер возвращает `true` и при пустом реестре, но `passCompleted &= …` не спасает от четырёх `false`.)
  3. *Достаточно показывать «Реестр пустой» по `ScanProgressTotal==0`* — **опровергнуто (скрытый баг в постановке)**: `ScanProgressTotal==0` и пустой `_store` наступают и при недоступном сетевом томе — `EnsureStoreLoaded` ловит `IOException` из `Load()` (кейс 20) и оставляет стор пустым. Признак «пусто» по числу записей соврал бы «Реестр пустой» при отвалившемся шаре. Нужен отдельный признак успешной загрузки.
- **Корень:**
  - курсорные сканеры при пустом реестре никогда не возвращают `passCompleted=true` (нечего коммитить), поэтому цикл полного прохода `_scanPassInProgress` не закрывается;
  - `RunTick` не имел раннего выхода для пустого реестра и на каждом кванте крутил `_scanIterationCount`;
  - стор не различал «загрузили и записей нет» и «загрузить не удалось» — нельзя было безопасно показать «Реестр пустой».
- **Доказательство:** `VelumProductRegistryBrokenLinkScanner.Tick` — ветка `if (items.Count == 0) { if (passActive) { … passCompleted = true; } … return passCompleted; }` (при `passActive==false` → `false`); `RunTick` — `Interlocked.Increment(ref _scanIterationCount)` выполняется до сканеров и без ветки пустого реестра.
- **Исправление:**
  - `VelumProductRegistryIntegrityScheduler`: поле `_storeLoadedOk` (true только после удачного `Load()`; сбрасывается в catch `EnsureStoreLoaded`) и свойство `IsRegistryEmpty` (`_storeLoadedOk && GetAllItems().Length==0`);

## Эвристики (случай 21)

- **E43. «Пустой вход» обязан иметь явный ранний выход в планировщике, а не полагаться на «проход завершится».** Конвейер курсорных сканеров, где «завершение прохода» фиксируется коммитом pending, при нулевом входе никогда не доходит до коммита (коммитить нечего → флаг прохода не ставится → внешний цикл-счётчик никогда не сбрасывается и крутится вхолостую). Правило: если у конвейера есть счётчик/цикл «полных проходов», в его диспетчере обязан быть ранний выход при пустом наборе, выполняющий ровно те же действия по «закрытию» состояния, что и нормальный конец прохода. Отдельно: признак «пусто» должен опираться на успешность загрузки данных, а не на пустоту структуры (пустая структура = и «нет данных», и «не удалось прочитать»). См. случай 21, E41.

## Эвристики (случай 22)

- **E44. «Вход есть, но источник данных мёртв» — это третье состояние гейта, наряду с «пусто» и «есть данные».** Если внешний источник (сетевой том, VPN-шара) может стать недоступным, а структура в памяти при этом остаётся непустой от прошлой удачной загрузки, то гейт «сканировать или нет» обязан иметь явное состояние «источник недоступен»: ранний выход **до** любых тяжёлых обращений к тому (иначе каждый тик платит таймаут) и до инкремента счётчика прогресса. Проверку недоступности нельзя делать на каждом такте — нужна редкая проба по настраиваемому расписанию, а снятие пометки — только по успешной пробе. ## Случай 23. Панель агента: «Каталог реестра недоступен» на работе при живом сетевом диске `Z:\` (реестр в локальной сети)

- **Дата / сборка:** 2026-09-30, `bin\Debug\velum.dll` (после случая 22; жалоба: «на другом компе реестр подключён к `Z:\03_Производство\Реестр изделий`, сеть доступна, а панель пишет "Каталог реестра недоступен" — видимо, доработка прицепилась к IP-пути»)
- **Симптом:** при корне реестра на mapped-диске (`Z:\...`) с живой локальной сетью гейт недоступного корня (случай 22) ошибочно срабатывает: панель показывает «Каталог реестра недоступен», счётчик сканирования не растёт. На VPN-машине (корень UNC `\\192.168.10.66\dfs\...`) поведение корректное — баг проявляется только на букве диска.
- **Область:** `Configuration\VelumAppConfig.cs` (`GetDocumentRootPath`, `TryCreateDirectory`), `ReactiveCore\Export\VelumRelativeDocumentPathResolver` (`GetRoot`), `VelumProductRegistryIntegrityScheduler.ProbeRegistryRootAvailable`, `Common\VelumProjectSettingsForm.*`.
- **Гипотезы и проверки:**
  1. *Доработка прицепилась к IP-адресу/UNC и «не понимает» букву диска* — **опровергнуто кодом**: `ProbeRegistryRootAvailable` вызывает `VelumPathExists.DirectoryExists(root)`, а тот работает с любым путём; UNC-специфики в гейте нет.
  2. *`VelumPathExists`/circuit-breaker помечают mapped-диск «недоступным»* — **опровергнуто**: `NetworkRoot(path)` возвращает пустую строку для буквы диска (`Z:`), circuit-breaker сетевых корней сюда не применяется.
  3. *`DirectoryExists(root)` для `Z:\...` даёт `Unknown` из-за таймаута* — **опровергнуто**: на живом локальном диске проверка мгновенная; но проверялся не тот путь — см. пункт 4.
- **Корень A (настоящая причина): порочный круг в гейте корня.** `ProbeRegistryRootAvailable` начинался с `if (!_storeLoadedOk) return false;`. Флаг `_storeLoadedOk` выставляется в `true` только внутри `EnsureStoreLoaded`, вызываемого из `RunTick`. Но `RunTick` ставится в очередь лишь после `ShouldSkipScanForUnavailableRoot` → `ProbeRegistryRootAvailable`. На старте `_storeLoadedOk == false` → проба всегда `false` → корень помечается недоступным → `QueueTick` не вызывается → `EnsureStoreLoaded` не выполняется → `_storeLoadedOk` навсегда `false`. Скан не запускается никогда, панель бессрочно «Каталог реестра недоступен» — на любом корне (и `Z:\`, и UNC). Ошибка сделана в случае 22 и проявляется при живом каталоге.
- **Корень B (вторичный, тихий): одиночные `\` в литералах.** В `VelumAppConfig.GetDocumentRootPath` UNC-префикс определялся `@"\"` — **один** обратный слэш (дефект E14). `StartsWith(@"\")` истинно для любого пути, начинающегося с `\`, в т.ч. `Z:\`, поэтому корень `Z:\03_Производство\Реестр изделий` ошибочно шёл по UNC-ветке и получал хвостовой `\`. Аналогичные мёртвые префиксы `\\?\` были в `VelumProductRegistryStore.BuildFilePathKey` и `VelumProductRegistryIntegrityRules.GetExtension`.
- **Доказательство:** A — `ProbeRegistryRootAvailable` (стр. ~1165) читал `_storeLoadedOk`, записываемый только в `EnsureStoreLoaded` (1099/1111), который достижим лишь из `RunTick` после пройденной пробы; порядок `OnPulseCompleted` → `ShouldSkipScanForUnavailableRoot` → `QueueTick` → `RunTick` → `EnsureStoreLoaded`. B — `od` показал один байт `\` в `VelumAppConfig.cs:197`.
- **Исправление:**
  - `ProbeRegistryRootAvailable`: убрана зависимость от `_storeLoadedOk` — проба проверяет только доступность каталога (`VelumPathExists.DirectoryExists(root)`), пустой путь → true; порочный круг разорван (реальная недоступность тома по-прежнему ловится таймаутом `DirectoryExists` → `Unknown`/`No` → `false`);
  - `VelumAppConfig.GetDocumentRootPath`: литералы → `@"\\"` (правились скриптом с литеральными заменами, байты проверены `od`);
  - `VelumProductRegistryStore.BuildFilePathKey` и `VelumProductRegistryIntegrityRules.GetExtension`: `@"\\?\UNC\"`, `@"\\?\"`, срез `@"\\" + path.Substring(8)`.
- **Проверка:** `MSBuild velum.csproj -t:Build -p:Configuration=Debug` (VS 18) → EXIT=0, `bin\Debug\velum.dll` обновлён. Ручная: корень `Z:\03_Производство\Реестр изделий` при живой сети — обычное «Сканирование №N …»; при обрыве сети — «Каталог реестра недоступен», счётчик не растёт; после восстановления — скан возобновляется.
- **Эвристики:** → E45, E46

## Эвристики (случай 23)

- **E45. Любой литерал с обратным слэшем писать через `Path.DirectorySeparatorChar` или проверять байты — `@"\"` в C# это ОДИН символ.** Ошибка E14 (тулзы «съедают» один `\`) уже дважды ломала проект: сначала каскадом CS1010, теперь — **тихо**: `StartsWith(@"\")` компилируется без ошибок, но истинно для любого пути, начинающегося с разделителя, в том числе для `Z:\`. Диагностический признак: код, задуманный как «начинается с `\\` (UNC)», ведёт себя как «начинается с `\`» — UNC-ветка перехватывает буквы дисков и портит пути. Для сравнений префиксов использовать `Path.DirectorySeparatorChar`/`Path.AltDirectorySeparatorChar`, для UNC — `new string(Path.DirectorySeparatorChar, 2)`. После правки строк с путями — сборка MSBuild (E13) и, при подозрении, проверка байтов (`od`/`grep`): успешная компиляция не доказывает корректность литерала. См. случай 23, E13, E14.
- **E46. Гейт не должен зависеть от состояния, которое само устанавливается только по прохождении гейта.** `ProbeRegistryRootAvailable` требовал `_storeLoadedOk`, а флаг выставлялся лишь после `EnsureStoreLoaded` внутри `RunTick`, куда попадают только при пройденной пробе — замкнутый круг: гейт блокирует единственный код, который мог бы его разблокировать, и «недоступно» становится вечным. Правило: условие раннего выхода проверяет **внешний факт** (доступность каталога/тома), а не производный флаг внутренней загрузки; производные флаги («загрузилось», «пусто») — для классификации результата, не для гейта. Диагностический признак: баг воспроизводится на старте всегда и на любом пути, лечится только перезапуском (или если пометку снимает другой код). См. случай 23 (корень A), E43, E44.

## Эвристики (случай 24)

- **E47. Имя вкомпилированного ресурса формы определяется первым top-level классом файла, а не именем файла.** В не-SDK csproj MSBuild выводит имя `.resources` из **первого** типа, объявленного в `.cs`, а не из имени файла (связка `.cs`↔`.resx` по `<DependentUpon>`). ## Эвристики (случай 26)

- **E51. Результат дорогого COM-резолва (активный документ, edit-target сборки) обязан кэшироваться, а не пересчитываться на каждом вызове.** `VelumSolidDocumentEditContextResolver.Resolve` выглядит как «дешёвое чтение контекста», но внутри — `IActiveDoc2` и `AssemblyDoc.GetEditTarget()`, а вызывается он десятки раз за такт из моста, обхода плашек мозаики и оркестратора. Правило: COM-резолв держать в кэше, обновлять его один раз за такт на UI-потоке SW (`ResolveFresh`) и инвалидировать по событиям смены документа/сессии. Диагностический признак: частота подвисания совпадает с пульсацией и зависит от размера сборки, а не от типа пробы; в коде — один и тот же метод-резолв, вызываемый из нескольких мест одного такта без общего результата. См. случай 26.
- **E52. Дорогие COM-проверки в UI-потоке SW обязаны гейтиться по смене входных данных, а не повторяться каждый такт.** `RefreshInapplicableProbesInSnapshot` на каждом пульсе заново читал CPM-свойства по всем ключам снапшота; сам снимок не меняется, если не сменился документ/edit-target и флаг «экспорт требуется». Правило: для повторяющейся на пульсе проверки вычислять дешёвый ключ контекста (путь/identity документа, флаг свойства) и выполнять дорогую часть только при его изменении; для «залипших» результатов хранить множество уже обработанных ключей. Диагностический признак: пробоотбор по одному и тому же документу повторяется каждый такт при неизменном документе. См. случай 26, E50.

## Эвристики (случай 25)

- **E49. Проба метрики не должна сама «дотягиваться» до неподходящего типа документа ради того, чтобы вернуть хоть какой-то результат.** Проба, семантически привязанная к конкретному типу документа (PDF-путь — к чертежу или источнику-детали, а не к сборке), обязана возвращать «неприменимо», а не подставлять активный документ как fallback. Диагностический признак: на документе одного типа (сборка) UI подвисает на COM, а на других типах нет; в коде — `?? ActiveModelDoc`/`ActiveModelDoc2` в ветках, где ожидается документ другого типа. Правило: тип документа проверять **до** выбора `modelDoc`; при несоответствии — ранний `return false` (проба неприменима), а не «взять активный». См. случай 25.
- **E50. Такт пульса не должен безусловно трогать COM SolidWorks, даже если кажется, что обход снапшота «дёшев».** `PrunePublishedSnapshotForEditContext`/`RefreshInapplicableProbesInSnapshot` на каждом пульсе обходят все ключи снапшота и для неприменимых проб дёргают пробоотбор; если пробоотбор по какой-то ветке уходит в COM, каждый пульс платит COM-опрос в UI-потоке SolidWorks — отсюда «сканирование раз в секунду» и подвисание. Правило: на пульсовом такте (без изменения документа) допускаются только обращения к закэшированным данным; любой путь от `OnPulseBeforeGomeostasis` до COM должен быть отсечён либо гейтом «документ изменился», либо тем, что неприменимые пробы не доходят до COM (как в случае 25). Диагностический признак: периодическое подвисание с частотой пульсации, строго зависящее от типа активного документа; помогает перепись всех вызовов между `OnPulse…` и `ModelDoc2`/`CustomPropertyManager`. ## Эвристики (случай 27)

- **E53. Маркер достоверности снимка обязан сбрасываться целиком, а «хост-глобальные» значения не должны блокироваться COM-статусом.** Если достоверность определяется несколькими флагами (`timedOut || isStale || lastErrorKind`), а метод «снять недостоверность» обнуляет только часть, оставшийся флаг делает снимок вечно недостоверным — и любой `release` по нему заблокирован. Диагностический признак: состояние «залипает» именно при закрытых документах и лечится только перезапуском. Отдельно: если параметр зависит от значений, приходящих **не** из COM-проб (реестр, BOM-обмен с 1С), то в правилах отпускания он обязан относиться к host-global-набору, иначе отсутствие удачного COM-опроса никогда не отпустит его. См. случай 27.
- **E54. Сканирующий компонент без pending-флага прохода ломает симметрию abort и очередность метрик.** Все курсорные сканеры живут по циклу `BeginPendingPass → … → CommitPendingPass` и корректно откатываются при смене области (E29/E31); сканер, делающий полный проход «на одном тике» без флага, (а) публикует результат раньше остальных и (б) при `AbortDiscoveryPassesUnlocked` оставляет незакрытый pending. Правило: у любого сканера обязан быть флаг активного прохода, коммит — только при незавершённом/непрерванном проходе, а периодичность тяжёлого прохода — настраиваемой. Диагностический признак: одна метрика загорается/гаснет «вне очереди» остальных; после смены open/closed-области на середине прохода состояние не восстанавливается до перезапуска. См. случай 27, E29, E31, E43.

## Случай 32. Форма логов: «Не выбрана ни одна сессия» при отмеченных флажках (кнопка «Просмотр»)

- **Дата / сборка:** 2026-10-04, `bin\Debug\velum.dll`.
- **Симптом:** в окне «Логи агента» пользователь отмечает сессии флажками в чек-списке, кнопка «Просмотр» становится активной, но по нажатию пишет «Не выбрана ни одна сессия». Воспроизводится на любой из трёх вкладок при выборе мышью по флажку. Через «Выделить все»/«Снять все» симптом не проявляется.
- **Область:** `Common\Logs\VelumLogsForm.cs` (`OnSessionItemCheck`, `CollectSelectedIndices`, `RefreshButtons`, `SetAllChecked`), `Common\Logs\VelumLogSessionRules.cs`.
- **Гипотезы и проверки:**
  1. *Кнопка активна, значит выбор где-то есть — баг в самом обработчике «Просмотр»* — **опровергнуто**: `OnViewClick` корректно читает `CollectSelectedIndices()`, проблема в пустом результате.
  2. *`CollectSelectedIndices` берёт только видимые (отфильтрованные) строки* — **опровергнуто**: метод обходит `GetActiveItems()` (весь список вкладки), фильтр ни при чём.
  3. *`CheckededListBox.CheckedItems` пустеет из-за перевязки источника* — **опровергнуто**: выборка вообще не читает `CheckedItems`, она читает поле `SessionListItem.Checked` (модель строки).
  4. *`RefreshButtons` считает иначе, чем `CollectSelectedIndices`* — **корень**: `RefreshButtons`/`CountChecked` считают по контролу (`list.CheckedItems.Count`), поэтому кнопка честно активируется; а `CollectSelectedIndices` читает модельный флаг `item.Checked`, который `OnSessionItemCheck` никогда не проставлял.
- **Корень:** у `CheckededListBox` состояние чекбокса живёт в контроле, а модель `SessionListItem.Checked` — отдельное. `OnSessionItemCheck` только перерисовывал кнопки, но не писал `e.NewValue` в `item.Checked`. При клике по флажку контрол отмечает строку (кнопка активируется по `CheckedItems`), но модель остаётся `false` → выборка по модели пуста → «не выбрано ни одной». «Выделить все» работает, потому что `SetAllChecked` пишет `item.Checked` напрямую.
- **Доказательство:** `VelumLogsForm.cs` до правки: `OnSessionItemCheck` не обращался к `item.Checked`; `CollectSelectedIndices` — `if (item.Checked && item.Info != null)`; `RefreshButtons` — `list.CheckedItems.Count`. Отсюда рассинхрон «кнопка активна / выборка пуста».
- **Исправление:**
  - `OnSessionItemCheck` теперь проставляет `item.Checked = e.NewValue == CheckState.Checked` по `e.Index` (событие приходит ДО применения состояния к контролу, поэтому модель обновляется явно из `e.NewValue`);
  - выборка вынесена в чистый `VelumLogSessionRules.CollectSelectedSessionIndices<T>(items, isChecked, sessionIndex)` (без WinForms), `CollectSelectedIndices` делегирует в неё — по образцу случая 31;
  - регрессия: `tests\VelumLogSessionRulesTests.cs` — 5 тестов на выборку, включая пары «до/после» (модель не проставлена → пусто; модель проставлена → выбор есть) и пропуск строк без привязанной сессии.
- **Проверка:** `dotnet test` → 219/219 успешно (было 214); `Build-Velum.ps1 Debug` → EXIT=0. Ручная (в SolidWorks): отметить сессии флажками → «Просмотр» формирует отчёт; «Выделить все»/«Снять все» — как раньше; при пустом выборе «Просмотр» по-прежнему пишет «не выбрана ни одна сессия».
- **Эвристики:** → E58.

## Эвристика (случай 32)

- **E58. `CheckededListBox`: состояние чекбокса и модель строки — разные источники; выборка обязана читать тот же, что и активация кнопки.** `list.CheckedItems`/`GetItemChecked` (состояние контрола) и собственный флаг модели (`item.Checked`) синхронизируются только вручную: `ItemCheck` приходит ДО применения нового состояния, поэтому в модели надо писать `e.NewValue`, а не `e.CurrentValue`. Симптом рассинхрона: кнопка действия активируется (считает по контролу), но по нажатию сообщает «ничего не выбрано» (считает по модели). Правило: либо вся логика читает контрол, либо вся — модель, и обработчик `ItemCheck` обязан обновлять модель. Проверять регрессией пару «флажок щёлкнули → выборка видит». См. случай 32, E57.
