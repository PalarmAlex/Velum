# DEBUG_CASEBOOK_REVISION.md — Регламент ревизии базы случаев

Назначение: **база случаев (`DEBUG_CASEBOOK_*.md`) полагается истинной на 100%** — агент начинает разбор бага с неё и берёт известный корень как факт. Если в базе есть внутреннее противоречие (случай A говорит «X истинно», случай B — «X ложен»), агент зацикливается: он не может одновременно верить обоим. Поэтому базу надо **регулярно перетряхивать**: искать противоречия, снимать их правкой описаний (когда вся база указывает на одну ошибку описания) либо выносить в список на доп. проверку (когда уверенности нет).

Этот файл — **реестр ревизий**: что уже снято, что спорно, как проверять. Он не заменяет случаи, а ссылается на них.

## 1. Когда делать ревизию

- **После каждого нового случая** (обязательная часть работы наравне с регресс-тестом и справкой). Минимум — пройтись чек-листом раздела 3 по новым эвристикам и по всем старым, которые они затрагивают.
- **Выборочно — при первом же обращении к базе** за сессию: если искомый симптом пересекается с эвристикой из раздела 4 («спорные»), не брать её на веру, а проверить по коду/тесту.
- **Планово** — когда в DXF/реестровой/метрической линии закрыто ≥ 3 новых случая подряд (это линии с наибольшей плотностью взаимных перекрываний).

## 2. Категории находок

| Категория | Что это | Что делать |
|---|---|---|
| **Коллизия номера** | Один номер (случая или эвристики) используется дважды для разного содержания | Перенумерация **запрещена** правилами ведения. Оставить оба, добавить пометку `⚠ Коллизия номера` со ссылкой на часть книги; при ссылке всегда уточнять часть (CB1/CB2) и номер случая |
| **Устаревшее утверждение** | Более поздний случай/код опроверг раннюю формулировку, но текст остался | В раннем месте — пометка `⚠ УТОЧНЕНО случаем N (E…)` со ссылкой; правка допустима, т.к. вся база указывает на одну ошибку описания |
| **Описка статуса** | Указатель/статус противоречит фактическому исходу случая | Исправить описательно (без изменения корня/даты) |
| **Сомнительный случай** | Противоречие НЕ снимается текстом — нужна эмпирика (ручная проверка или доп. тест) | Внести в раздел 4 «Спорные случаи», не править утверждения |

**Правило безопасности:** править текст описания можно **только** когда противоречие снимается всей базой (есть более поздний случай с доказательством по коду/логам/тесту, либо явная опечатка). Если для снятия нужен эксперимент на живой машине — это **не** правка описания, а запись в спорные.

### 2.1. Уровни доверия [A]–[D]

Каждому случаю/эвристике присваивается **дискретный** уровень доверия — не числовой вес. Числа плавают при каждой ревизии и требуют пересчёта всей базы; дискретный ранг стабилен, дёшев и читается без калибровки.

| Уровень | Что значит | Как брать в работу |
|---|---|---|
| **[A] Живой регресс / код HEAD** | Подтверждено зелёным регресс-тестом, реально существующим в HEAD, или прямым чтением текущего кода | Факт без перепроверки |
| **[B] Лог / ручной прогон** | Корень найден эмпирически (лог SolidWorks, ручной сценарий), но автотеста нет | Факт; при сомнениях — быстрый ручной повтор |
| **[C] Текст базы / git-факт** | Снято более поздним случаем, опечаткой или фактом из `git` | Верно логически; при первом обращении сверить якорь с кодом |
| **[D] Спорное / не снято** | Из раздела 4; противоречие текстом не снимается | НЕ брать на веру; работает **стоп-гейт** (см. 4.0) |

**Присвоение.** Новый случай по умолчанию: **[B]**, если есть лог/ручной прогон; **[C]**, если снято текстом/git. **[A]** — только когда назван конкретный зелёный тест из HEAD. **[D]** — всё, что попало в раздел 4. Уровень пишется коротким тегом в шапку/заголовок случая. Эмпирика (A/B) всегда бьёт текст (C): при конфликте текст не удаляется, а помечается `⚠ УТОЧНЁН` и понижается до уровня живого свидетельства. Для COM-зависимого кода (SolidWorks) уровень **[A]** достижим только для чистых правил, вынесенных в тестируемые функции (напр. `VelumDxfGeometryStampRulesTests`); порядок вызовов в живом Helper остаётся максимум **[B]**.

**Эталон присвоения (CB2):** решение «regen пишет pending при расхождении отпечатка» (E104/62) — **[A]** (`ShouldWriteDxfGeometryFingerprint`+`NotifyPartGeometryModified` покрыты `VelumDxfGeometryStampRulesTests`); удалённый токен-дискриминатор E98 — **[C]** (git-факт удаления); «встряска» случая 44 с неустановленным корнем — **[D]**.

## 3. Чек-лист ревизии (проход по новому случаю)

1. **Новый номер не занят?** Поискать `## Случай N` и `E{номер}` по всем `DEBUG_CASEBOOK_*.md`. Занят → пометка о коллизии.
2. **Новая эвристика не противоречит ли старой?** Если новая обобщает/сужает/отменяет старую — в старой пометка `⚠ УТОЧНЕНО/ОТМЕНЕНО случаем N`. Эталон: E72←E73 (отмена), E99←E104 (уточнение).
3. **Тот же симптом уже разобран?** Если да — это должен быть **дополнением** к существующему случаю, а не новым (правило ведения). Если заведён новым — проверить, не создаёт ли он ложную пару «A ⟺ ¬A».
4. **Ссылки на код живы?** Якоря `Файл.cs:строка`, имена методов сверить с текущим кодом (`search_file_content`). Расхождение → пометка или правка якоря (это не изменение корня).
5. **Статус в указателе = фактический исход?** (Эталон описки: случай 8 был помечен `WM_CHAR`, тогда как починка — `WM_KEYUP`.)
6. **Нет ли «трёх заплаток на одну дыру»?** Если один симптом (например «статус горит, плашки молчат») закрыт несколькими случаями с **разными** механизмами — записать в спорные (см. раздел 4, группа «статус↔плашки»).

## 4. Спорные случаи (нужна доп. проверка, текстом НЕ снимаются)

Формат: что оспаривается → как проверить → вариант закрытия (новый/исправленный регресс-тест или ручная проверка).

### 4.0. Стоп-гейт (правило входа)

Если в реестре есть спорный случай уровня **[D]**, **релевантный текущей задаче** (совпадает симптом/подсистема/эвристика), то **сначала закрывается противоречие, и только потом заводится новый случай**. Иначе новый случай наслаивается на непроверенное основание и сам становится **[D]** — база разрастается петлями.

Порядок при срабатывании гейта:
1. Найти в разделе 4 запись, покрывающую спор (`4.1`…`4.N`).
2. Прогнать её «Как проверить» (регресс / ручной сценарий / `git`).
3. Закрыть: повысить доверие до [A]/[B]/[C] либо зафиксировать решение оператора.
4. И только затем — новый случай по исходной задаче.

Исключение: если закрыть спор прямо сейчас невозможно (нужна живая машина/SolidWorks, которой нет), новый случай заводится, но **обязательно** с явной ссылкой на `4.N` и уровнем **[D]**, чтобы не притворяться достоверным.

### 4.1. Линия DXF-устаревания: случаи 56 → 62 (эвристики E95–E106)

- **Что оспаривается.** Пять случаев подряд лечат одну метрику «DXF устарел» взаимно перекрывающимися дискриминаторами: форс `pending=export+1` (E95/56), save-контур (E96/57), токен эскизов (E98/58), различие Modify/Regen (E99/59), regen-щит (E100/60), перенос щита (E101/61), отпечаток геометрии (E102–E106/62). Код подтвердил: форс E95 **жив** (`TrySyncPendingGeometryStamp` вызывается из 3 мест) и работает **под** гейтом отпечатка; токен-дискриминатор E98 удалён как мёртвый (примечание к случаю 58). E99 помечена устаревшей в пользу E104.
- **✅ СНЯТО (2026-11-23, чтение кода HEAD, уровень [A]).** Подозрение «часть заплаток (E100/E101 regen-щит) теперь избыточна поверх отпечатка E102» **опровергнуто живым кодом**: `_partRegenSinceLastSave` реально **читается** в `VelumExportDocumentationGeometryStampHelper.NotifyPartSaved` (`:690–691`) как аргумент `regenFromUpdateCommand` предиката `ShouldWriteDxfPendingAfterSave`, а выставляется в начале `NotifyPartGeometryModified` (`:260–266`, логика E101 — до всех ранний return). То есть regen-щит **не избыточен**, а функционален: он нужен post-save контуру (случаи 57/60), чтобы отличить regen-грязь от genuine-правки, подавленной save-контуром. Это согласуется с текстом самого случая 62 (E104: regen обязан уметь писать pending при расхождении отпечатка). Утверждения E100/E101 повышены до **[A]**.
- **Риск (остаётся).** Это самая плотная линия эвристик; любое новое утверждение про pending почти наверняка с ней конфликтует. Снято лишь подозрение об избыточности E100/E101 — **сквозная проверка порядка вызовов в живом Helper на реальной SolidWorks не выполнена** (COM-зависима, автотест невозможен).
- **Как проверить (регресс-тест).** `VelumDxfGeometryStampRulesTests` уже покрывает чистые правила. **Не покрыт** порядок вызовов в живом Helper (гейт отпечатка → форс → дожим post-save) — он COM-зависим. Нужно: сквозной ручной прогон сценариев случаев 56/57/58/59/60/61/62 в SolidWorks одним заходом (сквозной чек-лист «сценарий → ожидаемо → факт»).
- **Вариант закрытия:** сквозная ручная проверка DXF-цепочки на живой машине (заполнить таблицу «сценарий → ожидаемо → факт»). Избыточные дискриминаторы по итогам не выявлены (E100/E101 подтверждены живыми), поэтому ревизионный случай на удаление **не требуется**.

### 4.2. Группа «статус панели ↔ плашки метрик»: случаи 27, 37, 38, 39, 40, 44 (E53, E66–E70, E74)

- **Что оспаривается.** Один и тот же симптомокласс («Плохо» горит, плашки гаснут / наоборот) закрыт **тремя разными механизмами**: сброс маркера достоверности + host-global (27, E53), `ClearDocumentSpecificProbes`+registry-only публикация (37, E66), проверка `WasEngaged` в плашке (38, E67), публикация после тика (39, E69), событие `ProblemCache.Changed` (40, E70). Плюс **случай 44 (E74) — «встряска» кнопкой «Н» с явно НЕ УСТАНОВЛЕННЫМ корнем** (fix-first по указанию заказчика).
- **Риск.** Случай 44 маскирует корень детерминированным сбросом. Пока он стоит, нельзя утверждать, что 27/37/38/39/40 закрыли проблему полностью — возможно, 44 лишь заметает остаток. Это классическая петля для агента: «залипание» то лечится точечно, то встряской.
- **Как проверить.** Включить диагностику (как в продолжении случая 25: `SolidProbeEntryTrace`, логи `[Velum.Gate]`, `[Velum.EA]`, `OverallState`) и воспроизвести залипание **с выключенной встряской случая 44** — найти, на каком именно переходе снимается снимок/состояние. Регресс-тест объективно невозможен (статические синглтоны + COM), поэтому только ручная диагностика + последующий случай с настоящим корнем.
- **Вариант закрытия:** отключить `ShakeToNormHomeostasis()` → воспроизвести → установить корень → новый случай; после этого встряску 44 оставить как страховку (с пометкой, что корень теперь известен) либо убрать.
